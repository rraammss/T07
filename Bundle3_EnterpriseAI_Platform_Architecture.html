Track 1 · Cloud SI Landscape

What every cloud gives you

Learn the map once: three ways to buy SI, five building blocks on every cloud, and the rules on price and data that apply to all of them.
01

Three ways to buy SI

engineering problemTeams jump straight to building a platform when a finished assistant, or their own model, may fit better.
architecture focusBuy a finished assistant (Microsoft 365 Copilot, Gemini Enterprise, Amazon Q Business), build on a cloud platform, or run your own model on cloud compute.
LIVE DEMO · Place five company use cases on the three options and defend each choice.
02

Five building blocks on every cloud

engineering problemProduct pages make every cloud look different.
architecture focusModels, knowledge, agents, security and operations: one map, with Bedrock, Microsoft Foundry and Gemini Enterprise Agent Platform placed on it.
LIVE DEMO · Place each cloud’s services on the five-block map.
03

One request, three clouds

engineering problemEach cloud has its own endpoint, sign-in and request shape for the same model call.
architecture focusAWS signs with IAM, Azure uses Entra ID, GCP uses a service account; the frame, tokens and streaming from Path 1 stay the same.
LIVE DEMO · Send the same prompt to all three clouds and compare the raw requests.
04

Pricing and quotas

engineering problemThe same model can cost very different amounts depending on how you buy it, and quotas stop you before the budget does.
architecture focusOn-demand per token, provisioned throughput for steady load, batch for offline jobs at a discount; quotas per model and region limit all three.
HOMEWORK · Price one month of your ticket workload as on-demand, provisioned and batch.
05

Your data: residency and privacy

engineering problemRegulated data cannot go to any region, and teams are unsure whether the provider trains on their prompts.
architecture focusRegion choice, cross-region inference, data retention and the providers’ no-training commitments decide which models you may use.
LIVE DEMO · Check which models are available in your required region on each cloud.
Track 2 · AWS · Bedrock

Bedrock models, Knowledge Bases and AgentCore

Bedrock serves the models; Knowledge Bases, AgentCore and Guardrails turn them into an enterprise platform.
01

Models: catalog, and when to fine-tune

engineering problemModel access, regions and quotas differ per model, and teams fine-tune before trying a better prompt.
architecture focusThe Bedrock catalog and Converse API, cross-region inference, and custom models only when prompting and retrieval are not enough.
LIVE DEMO · Call two Bedrock models through the Converse API and read the quotas.
02

Knowledge: Bedrock Knowledge Bases

engineering problemBuilding ingestion, chunking and a vector store yourself takes weeks.
architecture focusKnowledge Bases ingest from S3, parse documents, chunk, embed and store vectors, then retrieve with citations.
LIVE DEMO · Load the SOP into a Knowledge Base and ask the ticket question.
03

Agents: AgentCore

engineering problemBedrock Agents Classic is in maintenance mode; new agents belong on AgentCore.
architecture focusAgentCore runs the agent loop, its Gateway exposes tools as MCP, and Memory, Identity and Observability come as services.
LIVE DEMO · Deploy a small agent on AgentCore with one tool behind the Gateway.
04

Security: IAM, PrivateLink, Guardrails

engineering problemModel calls go out over the internet with broad permissions and no content checks.
architecture focusIAM roles with least privilege, VPC endpoints through PrivateLink, and Bedrock Guardrails for content, PII and grounding.
LIVE DEMO · Call Bedrock over a VPC endpoint and block a PII leak with a guardrail.
05

Evaluate and operate on AWS

engineering problemNobody knows whether answers are good, or what they cost, until users complain.
architecture focusBedrock evaluations for quality, CloudWatch and invocation logs for usage, and cost allocation tags per app.
HOMEWORK · Run one evaluation job and build a tokens-and-cost view per app.
Track 3 · Azure · Foundry

Microsoft Foundry models, AI Search and agents

Microsoft Foundry, formerly Azure AI Foundry, brings models, search, agents and safety together in one Azure project.
01

Models: catalog, and when to fine-tune

engineering problemDeployment types, regions and quotas confuse first-time teams.
architecture focusFoundry projects and model deployments (standard, global, provisioned), Entra ID sign-in, and fine-tuning only when prompting and retrieval fall short.
LIVE DEMO · Deploy a model in Foundry and call it with Entra ID.
02

Knowledge: Azure AI Search

engineering problemSearch, vectors and permissions usually live in three separate systems.
architecture focusAzure AI Search combines keyword, vector and hybrid search with semantic ranking; Document Intelligence extracts text from PDFs and forms.
LIVE DEMO · Index the SOP in AI Search and run hybrid search on the ticket.
03

Agents: Foundry Agent Service

engineering problemTeams hand-build agent hosting, threads and tool calls.
architecture focusFoundry Agent Service hosts the agent loop, threads and tools, with connections to AI Search and other Azure services.
LIVE DEMO · Create an agent with a search tool and trace one run.
04

Security: Entra ID, Private Link, Content Safety

engineering problemShared keys, public endpoints and no protection against injection.
architecture focusManaged identities instead of keys, Private Link endpoints, Azure AI Content Safety with Prompt Shields, and API Management for token limits.
LIVE DEMO · Switch a key-based call to a managed identity and trip a Prompt Shield.
05

Evaluate and operate on Azure

engineering problemQuality and spend are invisible until something breaks.
architecture focusFoundry evaluations for quality, Azure Monitor and Application Insights for traces, and cost views per deployment.

Models: Gemini, Model Garden, and when to tune

Track 5 · Managed vs Self-Hosted

Your build or theirs?

From a managed API to your own GPUs: know the spectrum, what each step costs you in control and money, and how to decide.
01

The spectrum: API, endpoint, GPUs

engineering problemTeams see only two options, a managed API or their own data center.
architecture focusManaged API, then your own model on a managed endpoint (SageMaker, Azure ML, Vertex endpoints), then GPUs on Kubernetes (EKS, AKS, GKE).
LIVE DEMO · Serve one open model on a managed endpoint and compare it with the API.
02

What you gain, what you give up

engineering problemTeams either overvalue control or underprice the work of running it.
architecture focusManaged gives speed, scale and support; you give up control, tuning, visibility and some portability. Weigh it per building block.
LIVE DEMO · Compare your Path 1 build with a managed answer on the same ticket.
03

Lock-in and portability

engineering problemEvery managed service pulls your code toward one vendor.
architecture focusKeep a gateway and a stable contract in front, keep data and evals portable, and swap models or clouds behind it.
LIVE DEMO · Swap the backing cloud behind one gateway with no app change.
04

Cost break-even: tokens vs GPU hours

engineering problemAt some volume, paying per token costs more than renting GPUs, and nobody has done the maths.
architecture focusCompare monthly token spend with GPU hours plus the people to run them; volume, latency and data sensitivity move the line.
HOMEWORK · Find the break-even volume for your ticket workload.
05

Making the decision

engineering problemDecisions get made in meetings and forgotten.
architecture focusA one-page checklist: data rules, volume, quality, skills and exit plan, recorded as a short decision record.
HOMEWORK · Write a one-page decision for one workload.
Track 6 · Enterprise Rollout

Taking it live for the whole company

A safe base, clear rules on who may use what, one view of usage and cost, limits you can live with, and a plan to bring teams on board.
01

Landing zone: a safe base for SI

engineering problemEach team sets up its own accounts, keys and network paths to models.
architecture focusShared accounts or subscriptions, workload identity, private endpoints and no public egress, set up once by a platform team.
LIVE DEMO · Call a model over a private endpoint and prove the public path is closed.
02

Who may use which model and data

engineering problemAny team can call any model with any data.
architecture focusOrganization policies limit models and regions (SCPs, Azure Policy, Org Policy); data access follows the same rules as the rest of the company.
LIVE DEMO · Block a non-approved model for one team with a policy.
03

Usage and cost per team

engineering problemOne shared bill hides which team or feature spends the money.
architecture focusTag every call by team and app, set budgets and alerts, and report usage and cost back to each team monthly.
HOMEWORK · Build a monthly usage and cost report from tagged calls.
04

Quotas, limits and failover

engineering problemA quota limit or a regional outage takes the assistant down at the worst moment.
architecture focusKnow the quotas, request increases early, and keep a fallback region or model behind the gateway.
LIVE DEMO · Hit a quota and watch traffic move to the fallback.
05

Rolling it out to the company

engineering problemTools launch, nobody knows the rules, and adoption stalls.
architecture focusA platform team, an onboarding path for new apps, a clear usage policy, and the same rules for SaaS assistants like Copilot.
HOMEWORK · Draft the one-page usage policy and onboarding steps for a new team.
