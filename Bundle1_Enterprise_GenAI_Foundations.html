Track 1 · LLM Application Runtime

Trace the complete runtime path before adding frameworks: request construction, authentication, model inference, streaming, context growth, latency, and cost.
01

140GB of weights, zero enterprise records

engineering problemTeams confuse learned parameters with stored records and expect the model to know private or current data.
architecture focusWeights encode learned statistical patterns; runtime systems must supply current and enterprise context explicitly.
LIVE DEMO · Prove the boundary by testing public knowledge, private data, and intentionally missing facts.

One POST request: client → gateway → model → response

engineering problemSDKs hide the actual network, identity, routing, and inference path.

Token budgets: reject the request before inference

engineering problemPrompts appear to be text, but limits and billing operate on tokens and context windows.

Track 2 · Enterprise Data Access

Choosing How Private Data Reaches the Model

Do not treat every document problem as RAG. Select direct context, uploaded files, deterministic APIs, databases, or retrieval based on freshness, size, control, and evidence needs.
01

Four data paths: prompt, file, API, or retrieval

engineering problemA model may know general patterns but cannot automatically read your VPC, ticket system, or document repository.
architecture focusSeparate training-time knowledge, runtime context, tool access, and external storage as different trust boundaries.
LIVE DEMO · Create a data-access matrix for public, private, regulated, and rapidly changing information.
02

Five use cases mapped to the correct data-access pattern

engineering problemTeams prematurely build vector databases for small or deterministic problems.
architecture focusChoose by data size, update rate, query pattern, required precision, source authority, latency, and cost.
LIVE DEMO · Route five sample use cases to the correct access pattern and defend each decision.
03

One ingestion record: text + metadata + lineage + ACL

engineering problemPDF loading is not enough; extraction failures and bad metadata silently degrade every later stage.
architecture focusAcquisition, parsing/OCR, normalization, metadata, access controls, lineage, deduplication, and reprocessing.
HOMEWORK · Build an ingestion pipeline that emits clean text, metadata, lineage, and parse-quality signals.
04

Cached prefix vs fresh evidence: two different architectures

engineering problemRepeated context can be expensive, but caching does not make stale data correct or searchable.
architecture focusUse prefix caching for stable repeated content; use retrieval or APIs when data must be selected or refreshed.
LIVE DEMO · Measure cost and latency with and without a stable cached prefix.

One unauthorized document: prove retrieval blocks it

engineering problemRetrieval can expose content the caller was never allowed to see.
architecture focusPropagate user or workload identity, enforce document-level permissions, and filter before generation.
HOMEWORK · Test authorized and unauthorized retrieval against the same indexed collection.

RAG quality begins before search. Structure content, chunk intentionally, preserve relationships, and create evidence units that can be retrieved and cited.

One grounded answer: evidence in, citation out

LIVE DEMO · Build the smallest complete evidence-grounded answer pipeline.
02

Six chunkers, one document, six different seams

engineering problemArbitrary splits can separate headings, definitions, tables, code, or parent context.
architecture focusCompare fixed, token, recursive, layout-aware, semantic, and parent-child strategies by document type.
LIVE DEMO · Run multiple chunkers on one mixed-layout document and inspect retrieval consequences.
03

Eight metadata fields that control retrieval eligibility

HOMEWORK · Add metadata filters and show how they change eligible results.

Track 4 · Retrieval Engineering

Selecting and Ranking the Right Evidence

Dense, sparse, hybrid, reranking, and graph retrieval solve different failure modes. Production systems compose them instead of declaring one universal winner.
01

Dense retrieval: the paraphrase found without exact words

engineering problemExact wording may differ while intent remains similar, but identifiers and rare terms can be missed.
architecture focusEmbedding search with similarity metrics, filters, top-k selection, and approximate nearest-neighbor indexes.
LIVE DEMO · Build a dense search baseline and document its miss cases.
02

Sparse retrieval: the error code dense search misses

engineering problemNames, codes, stack traces, versions, and identifiers often require exact or weighted term matching.
architecture focusInverted indexes, BM25-style scoring, analyzers, normalization, stemming, and field weighting.
LIVE DEMO · Run queries where sparse retrieval clearly outperforms dense retrieval.
03

Two ranked lists fused with reciprocal-rank fusion

engineering problemDense and sparse rankings use incomparable score spaces and produce overlapping candidates.
architecture focusFuse ranked lists using rank-based methods such as reciprocal-rank fusion, then deduplicate and filter.
HOMEWORK · Build dense + sparse retrieval with transparent fused rankings.
04

Twenty candidates reduced to five by reranking

engineering problemFirst-stage retrieval favors speed and recall, not final ordering precision.
architecture focusUse a cross-encoder or model-based judge only on a controlled candidate set; measure quality against added latency.
LIVE DEMO · Rerank candidates and compare relevance gain, latency, and cost.
05

Three hops through ownership, dependency, and evidence

engineering problemSimilarity search is weak when the answer requires traversing ownership, dependency, chronology, or causal links.
architecture focusModel entities and edges; use graph traversal alone or combine it with text retrieval for supporting evidence.
HOMEWORK · Answer a multi-hop ownership question using graph relations plus source documents.
