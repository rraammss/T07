Track 1 · Agent Runtime & Harness

The loop that runs the agent, and the harness that holds it

An agent is a loop around a model; the harness owns state, tools, retries, limits and when to stop.
01

Six runtime states from observation to termination

engineering problemA hidden loop is difficult to debug, constrain, or stop.
architecture focusRepresent observe/sense → decide/reason → act → receive result → evaluate → continue/finish as runtime states.
LIVE DEMO · Build a visible loop with state transitions and termination reasons.
02

One unauthorized tool proposal rejected by the runtime

engineering problemAllowing model output to directly trigger side effects creates uncontrolled authority.
architecture focusParse structured decisions, validate against policy, authorize, execute outside the model, and return observations.
HOMEWORK · Implement a runtime that rejects unauthorized tool proposals.
03

Five hard limits that stop a runaway agent

engineering problemAgents can loop, overspend, repeat writes, or continue after the goal is met.
architecture focusSet time, step, token, cost, tool, confidence, and human-escalation limits.
HOMEWORK · Force a looping agent to terminate safely with a clear reason.
04

Three injected failures, three designed recovery paths

engineering problemPartial success and downstream failure can leave business systems inconsistent.
architecture focusDefine retryable vs terminal errors, compensation, rollback, manual repair, and incident evidence.
HOMEWORK · Inject failures at multiple steps and verify the correct recovery path.
05

RAG inside the agent: retrieve only when the task needs it

engineering problemTeams incorrectly position retrieval and agents as competing architectures.
architecture focusAn agent may decide when to retrieve, which source to query, whether evidence is sufficient, and what action follows.
LIVE DEMO · Extend a fixed RAG flow into agentic retrieval with evidence evaluation and retry.
Track 2 · Tool Engineering

How agents act on real systems, safely and repeatably

Production reliability depends more on tool contracts and execution controls than on clever prompts.
01

Three tool contracts: lookup, update, and submit

engineering problemAmbiguous descriptions or weak schemas produce incorrect tool selection and malformed arguments.
architecture focusUse precise names, descriptions, typed inputs, enums, required fields, stable outputs, and structured errors.
LIVE DEMO · Design and test schemas for lookup, update, and submit operations.
02

Read tool vs deploy tool: two different risk classes

engineering problemA search call and a deployment call must not share the same control model.
architecture focusClassify tools by side effects and require stronger authorization, confirmation, and audit for writes.
LIVE DEMO · Apply separate policies to read-only and side-effecting tools.
03

One idempotency key prevents a duplicate business action

engineering problemRepeating a timed-out write can create duplicate orders, tickets, or deployments.
architecture focusUse idempotency keys, operation state, replay detection, safe retry policies, and compensating actions.
HOMEWORK · Simulate a timeout after a write and retry without duplicating the business action.
04

Malformed tool output rejected before reasoning continues

engineering problemAPIs can return stale, partial, malformed, or adversarial content.
architecture focusValidate result schema, provenance, freshness, completeness, and error semantics before returning it to reasoning.
LIVE DEMO · Reject a malformed tool result and route to recovery.
05

Stack trace → repository → package → owner

engineering problemA stack trace alone does not identify repository, package ownership, release, or responsible change.
architecture focusUse repository search, dependency manifests, CODEOWNERS, commit history, PRs, and release metadata.
HOMEWORK · Map a stack trace to repository, package, owner, and likely introducing change.
Track 3 · Context & Memory Engineering

What the agent knows now, and what it remembers later

Decide what the agent sees now, what it keeps for later, and what it must forget.
01

One long run compacted: 40 turns into a working summary that still holds the facts

engineering problemLong agent runs overflow the context window and lose the details that matter.
architecture focusContext engineering decides what stays, what is summarised, and what is fetched back on demand.
LIVE DEMO · Run a 40-turn incident session, compact it, and show the agent still answers from the kept facts.
02

Five storage categories: state, history, episodes, facts, artifacts

engineering problemTeams mix current workflow state, chat transcript, and durable knowledge into one store.
architecture focusSeparate execution state, immutable event history, episodic memory, semantic memory, and domain knowledge.
LIVE DEMO · Map each piece of an agent run to the correct storage category.
03

Ten conversation turns, only two memories worth saving

engineering problemSaving every conversation turn creates noise, cost, privacy risk, and conflicting facts.
architecture focusExtract candidate memories, classify them, attach provenance and confidence, deduplicate, and require consent where appropriate.
LIVE DEMO · Implement a memory-write policy that rejects low-value content.
04

One memory query filtered by user, tenant, and freshness

engineering problemA similar memory may belong to another user, tenant, task, or obsolete context.
architecture focusFilter by identity and scope, rank by relevance and recency, and return provenance with every recalled item.
HOMEWORK · Retrieve memories with tenant isolation and freshness scoring.
05

A changed preference supersedes the old memory

engineering problemPreferences change, facts expire, and inferred memories may never have been true.
architecture focusSupport correction, supersession, expiration, deletion, conflict resolution, and user visibility.
LIVE DEMO · Update a remembered preference while preserving audit history.
Track 4 · Patterns & Orchestration

Workflow or agent? One agent or many?

Use a workflow when the steps are known and an agent when they are not; add agents only when one is not enough.
01

Agent decision inside a deterministic workflow

engineering problemTeams use model reasoning for sequences already defined by business process.
architecture focusKeep known transitions deterministic; invoke the agent only where interpretation or choice is required.
LIVE DEMO · Refactor a fully agentic process into a hybrid workflow.
02

Three planning patterns tested on the same task

engineering problemLong free-form plans can become stale, expensive, and detached from actual tool results.
architecture focusUse short-horizon planning, re-plan after observations, and reserve deterministic workflows for known sequences.
LIVE DEMO · Compare fixed workflow, plan-then-execute, and incremental planning on one task.
03

One agent or many? justify the split with one measurable reason

engineering problemSplitting roles can increase cost and failure modes without improving outcomes.
architecture focusChoose specialization, isolation, ownership, or parallelism as explicit justification; otherwise prefer one agent plus tools.
LIVE DEMO · Refactor an unnecessary agent team into a simpler design.
04

Supervisor + three workers + one versioned task graph

engineering problemWithout clear ownership, agents duplicate work or produce conflicting artifacts.
architecture focusDefine task decomposition, assignment, dependencies, shared constraints, artifact ownership, and join logic.
LIVE DEMO · Build a supervisor with specialist workers and a task graph.
05

One checkpoint survives a service restart

engineering problemA process waiting on a person or remote system cannot live only in memory.
architecture focusPersist state, pending actions, tool results, version, correlation IDs, and resume conditions.
LIVE DEMO · Pause a workflow, restart the service, and resume from the correct checkpoint.
Track 5 · MCP · Vertical Protocol

Agent down to tools and data, through one standard plug

MCP replaces one-off adapters with one standard plug from the agent down to tools and data.
01

N applications × M tools: the integration matrix MCP collapses

engineering problemEvery agent application independently integrating every enterprise tool multiplies maintenance and inconsistency.
architecture focusSeparate tool providers into MCP servers and consuming applications into MCP clients using a shared protocol.
LIVE DEMO · Draw the direct-integration matrix and refactor it into MCP boundaries.
02

Three scenarios classified correctly: native API, MCP, or A2A

engineering problemConfusing MCP with agent delegation leads to incorrect architecture.
architecture focusUse MCP for exposing tools, resources, and prompts to a model application; use A2A for delegating tasks to autonomous agents.
LIVE DEMO · Classify integration scenarios as native API, MCP, or A2A.
03

One MCP client discovers and invokes two server tools

engineering problemA client needs to know available capabilities and their structured contracts.
architecture focusInitialize capabilities, list tools/resources/prompts, inspect schemas, invoke operations, and handle protocol errors.
HOMEWORK · Build a server with discoverable enterprise tools and a client that selects one.
04

Authenticated MCP call with policy, audit, and secret isolation

engineering problemA standard protocol does not automatically solve identity, authorization, tenancy, or data leakage.
architecture focusBind authenticated identity to server policy, isolate tools, validate arguments, log calls, and protect secrets.
LIVE DEMO · Add authorization and audit controls to an MCP server.
05

Three bounded MCP servers instead of one integration monolith

engineering problemA shared server can become an uncontrolled integration monolith.
architecture focusDefine bounded servers, product ownership, compatibility, schema evolution, deployment, observability, and deprecation.
HOMEWORK · Design the final enterprise MCP platform and migration path.

Track 8 · Security & Governance

Can it be attacked, and who is allowed to do what?

Assume the agent can be attacked: limit its authority, check every action, and keep the audit trail.
01

One prompt injection hidden in a document, blocked before a tool call

engineering problemText an agent reads can carry instructions that hijack its next action.
architecture focusTreat retrieved and tool content as data, not instructions; check every proposed action against policy before it runs.
LIVE DEMO · Plant an instruction in a runbook and show the harness refuse the injected tool call.
02

Two memory attacks: poisoning and cross-tenant leakage

engineering problemLong-term memory expands the impact of injection and data leakage.
architecture focusProtect writes from untrusted content, enforce ACLs, encrypt data, minimize retention, and test cross-tenant isolation.
HOMEWORK · Run memory-poisoning and cross-user retrieval tests.
03

Approve, reject, edit, or take control: four explicit states

engineering problemA generic chat question is not enough for controlled approvals.
architecture focusModel approve, reject, edit, take control, timeout, and escalation as explicit transitions.
HOMEWORK · Add a review gate before a high-impact submission.
04

One audit record for every side effect

engineering problemWithout execution evidence, autonomous actions cannot be reviewed or operated safely.
architecture focusRecord caller, agent, policy, arguments, redactions, result, duration, retry, and business outcome.
HOMEWORK · Produce a searchable tool-execution audit record.
05

One protected branch, zero direct agent commits

engineering problemAn agent that can merge or deploy without gates becomes a production risk.
architecture focusUse protected branches, scoped credentials, approvals, signed artifacts, staged promotion, and rollback hooks.
LIVE DEMO · Open a branch and PR, trigger validation, and block direct production writes.
